Agent build contract · read first

EM-UI is a set of design decisions and small HTML/CSS primitives, not a framework to reproduce wholesale. The goal is predictable visual consistency with the fewest rules necessary for each screen.

1 · Start with the user task

Choose a page width, content groups and semantic actions. Do not copy every toolbar, metric or panel from a different template.

2 · Compose, never nest by habit

A search field, filter, button or bulk-action bar is a functional block—not automatically another enclosing card. Place related controls in a plain flex toolbar and keep the data surface separate.

3 · Reuse a tiny CSS vocabulary

Prefer .page, .section, .toolbar, .button, .field, .card, .table. Combine existing classes for meaning and size; do not mint project-specific style variants for ordinary controls.

4 · Omit what is not required

No filtering requirement means no filter markup, state or handlers. No batch operations means no selection column or bulk bar. A disabled or hidden demo switch is not a production feature architecture.

5 · Use the white → gray surface hierarchy

Use #FAFAFA for the outer application canvas and #FFFFFF for the content workspace and most cards; use white table bodies with gray column headers and quiet 1px solid #E8E8E8 outlines. Inputs, dropdowns and separately owned nested areas remain white. Headings and toolbars are open, with no enclosing border. Use 8px control gaps, 12px between toolbar and table and about 24px between major blocks.

6 · Keep behavior explicit

Use native button, label, input, select and real table headers. Implement loading, disabled, selection, API calls and permissions in the project; do not carry reference-demo JavaScript into production.

7 · Give each title one owner

Put page and multi-card group headings on the canvas; put one self-contained card title inside its card. Compact summary cards need only a light label. For table + toolbar compositions, the collection heading stays outside the data card. Avoid repeating a heading at both levels or adding a nested card just for a subsection. See Page composition → 3A. Title ownership.

8 · One Blue interaction system

Use --brand: #3C82F6 for primary actions, selected/active UI and focus. Do not use Amber or Charcoal as alternate primary colors. Keep status colors semantically meaningful.

9 · Compose, inspect, refine

Prioritize the main task, believable data and restrained hierarchy. Review desktop and mobile output for spacing, overflow, contrast, keyboard access, reduced motion and real state handling before delivery.

Visual craft + verification · v15

Inspired by Stageshow’s emphasis on polished composition and inspection, adapted for real, framework-free product interfaces. The aim is a UI that looks deliberate and works, not a decorative screenshot.

1 · Establish a focal point

Show the user’s core job first. One page heading, one clear primary action per local scope, and prominent content that answers the main question. Secondary tools stay quiet.

2 · Compose with restraint

Start with content and whitespace. No unnecessary KPI wall, repeated mini-cards, gradients, badges, eyebrow labels or ornamental panels. Hierarchy comes from size, position, tone and proximity.

3 · Keep examples believable

Sample names, numbers, statuses and timestamps should fit the scenario and agree across cards, rows and charts. Distinguish sample/mock data from live readings. Do not invent success states.

4 · Keep blue intentional

Use --brand on Primary, selected navigation, checked controls and focus. Use --brand-soft only for a genuine active/selected state. Use green/amber/red for real semantic status—not visual variety.

5 · Motion explains change

Use subtle 120–200ms transitions only when they clarify hover, state or arrival. Avoid perpetual decoration, animated dashboards and motion that competes with data. Respect prefers-reduced-motion.

6 · Verify the real screen

Inspect at 1440px, 1200px, 768px and 390px. Check page and element overflow, truncated names, table scrolling, selected/focus states, contrast, empty/error/loading states, keyboard use and action semantics. Correct the HTML/CSS before shipping.

Never force equal widths

Do not use equal fractions or a global 760px minimum as a default. A short status column should not take the same space as a long record name.

Prefer horizontal scroll to squeezing

The table wrapper owns overflow. If many columns cannot fit a mobile viewport, allow them to scroll instead of shrinking text to unreadable sizes.

Compact ≠ cramped

Use 13px cells, 12px headers, roughly 9px vertical padding and 16px horizontal padding. Two-line identity cells grow naturally; no forced row height.

More room is an opt-in

Choose data-density="comfortable" for complex editable cells or dense for exceptional high-density views. Do not globally resize forms or buttons.

Multi-select only for actual batch work

Render a checkbox column and contextual bulk bar only if a real multi-row operation exists. Show the bulk bar after selection; reset selected IDs when the result set changes.

Omit optional markup in projects

The reference has demo-only switches. Production pages render Search, Filter, Export and selection only when useful; native hidden handles dynamic states. Clear selection and update API queries when data context changes.

Choose row-action presentation

Omit the action column when records have no actions. For one frequent action, use a direct small Ghost button. For two or more secondary actions, prefer a 29px ⋯ icon trigger with a dropdown; optionally pair one direct action with the menu. Every item needs a real action and permission check.

Menus must escape table scrolling

Place a shared native popover outside .table-wrap so it is not clipped by horizontal overflow. Anchor it to the row trigger, close on Escape or outside click, support keyboard navigation and show only relevant options. Do not create empty or destructive-only menus.

Outline the surface, not the toolbar

The white table surface uses the same 1px #E8E8E8 border as other cards; reserve #FAFAFA for column headings or an optional table-title strip. Search, Filter and Export stay in an open toolbar on the white workspace, with white input/select controls. A contextual bulk-action bar may have a subtle border as a stateful panel; do not wrap each control group.

Accessible, predictable tables

Use TH scope, clear button labels and an explicit empty state. Pagination defaults to 25 rows when needed, with 10 / 25 / 50 / 100 choices; skip pagination for short fixed lists.

7. Paginate collection tables consistently

Pagination belongs to the table card footer and is part of the collection interaction model, not an optional decoration.

Default page size · 25

Use 25 rows per page for ordinary management and history tables. Offer 10, 25, 50 and 100 in the rows-per-page selector.

When to show it

Use pagination when the collection can grow beyond 25 records or is loaded from a pageable API. Skip it for small fixed configuration matrices and intentionally short lists.

Footer ownership

Left side: result range + rows-per-page selector. Right side: Previous, numbered page selector and Next. Keep pagination in the table surface footer, separate from the external toolbar.

Interaction behavior

Search, filters, sorting and page-size changes reset to page 1. Disable Previous/Next at the boundaries and do not request impossible pages.

8. Keep multi-select and bulk actions inside the table owner

Selection is part of the collection state. Keep the checkbox column in the table and show the contextual bulk-action bar immediately above the table surface, under the optional toolbar. They share one collection owner but do not share a visual card.

Selection column first

Put the row checkbox in the first narrow column. The header checkbox controls the visible page and uses an indeterminate state when only some visible rows are selected.

Bulk bar is conditional

Do not reserve an empty permanent bulk-action area. Reveal it only after selection, as a sibling below the optional toolbar and above the white table surface.

Count + clear + actions

Lead with “N selected”, provide Clear selection, then show only actions that are valid for all selected rows. Style irreversible actions as danger and confirm them when necessary.

Do not make selection ambiguous

Page navigation can preserve selected IDs. Search or filter changes should clear selection by default. Query-wide “select all results” must be an explicit separate action.

Notifications are page-level feedback, not section content. Place one notification region at the bottom-right of the viewport so success and outcome messages stay visible without shifting the layout.
